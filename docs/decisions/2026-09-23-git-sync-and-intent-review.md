# 决策记录：多机Git同步与意图层审阅

Status: implemented

## 问题

H机main与GitHub已发布分支一致，采集机落后两次提交，但两机各有未提交修复。只从H机覆盖会丢失采集端的答案恢复与provider协议修复；直接把所有未跟踪文件加入仓库又会引入旧接口脚本和运行资产。用户需要从流程意图审阅项目，而非逐文件审查庞大上游框架。

## 决定

在隔离副本上以GitHub main为共同基础，合并两机独有修复；相同transport补丁保留一份。将实际执行包装器依赖的cleanup模块、DSML边界测试、worker清理帮助程序和生命周期决策纳入版本管理。保留已有DeepSeek Harness pin及逐字一致的受管patch，不更换上游版本。

同步采用有来源快照和工作树检查的快进流程，仅发布main，保留机器本地的运行资产与旧未跟踪文件。仓库级Git设置阻止隐式merge pull，保留脚本可执行位。可视化使用Understand-Anything，分析入口、契约、关键检查及主流程；通用vendor代码和生成数据不逐函数展开。生成图与简要意图审阅文档版本化，临时分析文件忽略。

## 放弃的备选

**直接用H机覆盖采集机。** 两机独有修复不在同一提交里，机器“通常最新”不能代替差异判断。

**无差别加入未跟踪文件或强制清理。** 旧批次runner、旧ReAct接口工具与本地数据不属于当前可复现源码并集；保留本地文件，不改变运行任务。

**升级DSH到上游master。** 这是依赖升级，需要另外的兼容验证，本次相同pin和已版控patch足以同步实际改动。

**给全部vendor函数建图。** 用户审阅的是流程意图与注意点，函数级海量节点增加负担；保留到关键源码的证据指针即可。

## 代价与收获

需要逐项合并和核验，但避免丢修复或误把运行资产发布到GitHub。流程图是明确范围的代码快照，后续源码变化后需要更新，不能当永久正确的描述。

## 没有验证的部分

本次不做GPU训练、科学工具实跑或provider付费调用，不证明科学数据完全合格。Git对齐不含密钥、数据、模型和机器私有运行配置；完整论文代码审查及所有上游框架内部行为不在本轮范围。
