# 决策记录（Decision Records）

## 为什么需要

Agent 改代码很快，但留下的是**产物**，不是**判断**。几周后你会面对一堆跑得通的代码，却答不上来：
当初为什么不用更简单的方案？这个奇怪设计是妥协还是失误？

——**你失去了否决的能力，因为看不到被否决的备选。** 代码写"怎么做"，契约文档写"是什么"，
"为什么不是别的"没有任何地方放，就放这里。

不写的后果很具体：同一个权衡被反复重新讨论，或者被不知情的 agent 悄悄推翻。

## 什么时候写

**每个非平凡改动在同一次改动里新增或更新一条。** 非平凡 = 改变了行为、跨文件契约、流程与工具链、
测试策略、落盘/wire/配置格式，或任何维护者日后可能质疑的决定。改错别字、改路径、格式化豁免。
已有记录拥有该决定时**更新它**，不要新建重复的。

## 格式

文件名 `docs/decisions/YYYY-MM-DD-议题.md`：日期是**议题首次提出**之日，标题描述**议题**而非结论
（结论可能被推翻，议题不会）。`Status:` 行三选一：`proposed` / `implemented` / `rejected — 一句话原因`。
被否决的记录只在该理由能防止一个具体错误时保留，否则删掉。

正文骨架固定、顺序固定，直接复制：

```markdown
# 决策记录：<议题>

Status: proposed

## 问题
<当初要解决什么，为什么现有做法不够。必须能脱离后面的方案独立读懂。>

## 决定
<已落地用现在时描述实际存在的东西；未落地描述意图与未决问题。>

## 放弃的备选
<必填。每个真实考虑过的备选一段，加粗开头点明是什么，再说明为什么输。
 不要编造；确实没有就写"没有其他备选被考虑，因为 X"。>

## 代价与收获
<付出了什么，换来了什么。两个方向都写。"没有代价"几乎总是错的。>

## 没有验证的部分
<这次改动**没有**证明什么。防止"未验证"被默认当成"已验证"。>
```

`## 决定` 里不写 `## 方案` / `## 计划` / `## 验收标准` 这类提案期措辞——落地的事只有事实。

## 两条硬规则

1. **`## 放弃的备选` 必填。** 没有记录"打败了谁"的决定会招来反复重新争论——这正是本目录要防的失败。
2. **一条记录不能被编辑成另一个决定。** 写新的、新旧互相链接；代码搬家改名时只同步事实性内容（路径、名字），
   不动决定本身。

## 用法

它同时是你的复习材料：想重新理解一个模块，按时间读它的决策记录，看到的是"当时面对什么、选了哪条、
放弃了什么"，而不是一堆既成事实。检验 agent 是否真懂，问它一句：**"这条决定当初打败了哪个备选？"**
