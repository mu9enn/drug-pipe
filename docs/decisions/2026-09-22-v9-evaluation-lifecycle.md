# 决策记录：v9 测评启动与收尾的生命周期边界

Status: implemented

## 问题

v9 CPU DSH 启动时，源码解析的同步等待可能长于 MCP SDK 的默认请求期限；外层曾以首页 HTTP 200 和固定存活 75 秒误判插件就绪。CPU 测评结束后，GPU worker 向 SGLang 发 TERM 再无限 wait，导致评测结束仍占卡、队列无法进入评分。

## 决定

本轮只修正评测生命周期，不修改 DSH/tsx 的模块解析算法，不采用诊断阶段的路径映射或依赖副本。运行目录的启动策略为 initialize 和首次分页 tools/list 设置与外层总启动期限一致的 1800 秒预算；tools/call 和初始化之后的目录请求保留原选项。首次完整目录按 DSH 的公开名称规则核对固定 81 个工具。启动器必须同时看到本次 token 的目录验证记录与精确端口的正式 dsh web URL 公告，并确认进程存活，才能写结构化 framework.ready。完整参数 schema、技能与模型协议仍由既有 runner 在开始题目前验收。

GPU 清理使用有限期限的进程树 TERM/KILL，PID starttime 防止误杀复用 PID；排队 active=0 不再视为资源已释放。原作业在改动之前已经完成 175 次尝试，但存在两道 TRANSPORT 中断和 worker 收尾挂起。续跑复用原模型作业，仅重试两道基础设施中断题，max_workers=2；原始 173 条其余记录用 SHA256 检查不变。保留首轮 scores_fence_only，补跑评分单独写 scores_recovered_fence_only，并保存续跑前后记录摘要。

正在旧 cleanup 中等待的 worker 不依赖脚本热更新。新看护进程使用有界租约及清理帮助程序收尾；共用 run_worker.sh 的修改在原 shell 退出后安装，避免修改仍在读取的 shell 文件。

## 放弃的备选

**修改 tsx 扩展名搜索或大规模替换路径映射。** 这些是性能诊断原型，可能改变边界解析行为，用户明确只要求修复导致超时、握手失败和卡住的地方。

**继续加长固定存活检查。** 故障注入已经证明固定 75 秒也会通过后再退出；必须依赖真正的初始化状态。

**重跑全部 175 题。** 已有完成结果无需重算，且会改变测评统计口径。只针对两道有 TRANSPORT 证据的未正常结束任务续跑，模型 token/context 限制导致的失败保留。

## 代价与收获

启动上限较长，异常远端最多会占用 CPU 启动预算，但 GPU 的首次申请受就绪屏障保护。运行钩子绑定当前 SDK 路径和 DSH 名称规范，升级时需更新并测试。收益是状态可验收、期限明确、退出可回收，且原始结果与续跑结果均可追溯。

## 没有验证的部分

不承诺消除冷启动耗时；没有证明共享存储服务故障，也没有兼容性验证诊断阶段的 tsx 改法。本记录不代表测评准确率提升。作业和续跑最终状态以 docs/STATUS.md 及 runtime_repair_0922 记录为准。
