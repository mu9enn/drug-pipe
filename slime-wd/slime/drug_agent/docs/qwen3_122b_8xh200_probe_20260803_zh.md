# Qwen3.5-122B-A10B：8×H200 转换与训练探针报告

日期：2026-08-03。worker：`slime-train-8g128c-40967252-cfcd2`，8×NVIDIA H200（每卡 143771 MiB），host RAM 1025 GiB。

## 结论

- HF→Slime torch distributed checkpoint 已成功：16 个 `.distcp` 文件，共 244,319,908,688 bytes；tracker 为 `release`。训练时已从转换用 `TP1/PP8` 成功重分片加载到 `TP2/PP4/EP2`。
- `TP2/PP4/CP1/EP2/ETP1` 能在 8×H200 上完成 4501-token canonical SFT 的真实 forward/backward；一次 microbatch 为 27–33 秒。
- Slime 官方推荐的大 MoE 低精度主路径是 BF16 训练 + FP8 rollout，但单机 8×H200 无法容纳本模型的标准 BF16 全参 Adam。本文采用的是实验性容量路径：FP8 parameter gather、FP16 main params、BF16 main grads、FP8 Adam moments；仅把 moments 逐组转存 pageable CPU memory，master weights 保留 HBM。它必须以数值稳定性对照验证，不能等同于官方生产精度路径。
- pinned Megatron-Core/Transformer Engine 的 `blockwise` FP8 与 FP16 optimizer shard 不兼容；本环境必须用 `--fp8-recipe delayed`。
- 标准 TE FusedAdam 会让第一步已初始化的全部 moments 累积驻留 GPU，实测最后在 139.98/140.06 GiB 硬 OOM。项目补丁改为每个 bounded parameter group 更新后立即把 FP8 moments 的 raw bytes 转存 pageable CPU memory，再进入下一组；train-only SFT 最终完整单步成功。
- 4501-token SFT 成功结果：loss `0.2070251374`、grad norm `3.4294734`、actor train `85.68 s`、`52.53 token/s`；最紧 rank 使用 `131.78/140.06 GiB` HBM，host used/available 为 `489.14/536.25 GiB`。Ray job `raysubmit_sgwzKZ2b3vDLzUpx` 正常成功退出。
- 旧 ToolRL 探针使用 BF16 SGLang checkpoint；它在 TP8 权重加载后因约 30.5 GiB/GPU 的 rollout 权重没有留下 KV pool 而失败。这只排除了 **BF16 rollout**。换成 Slime 官方推荐的“BF16 Megatron actor + FP8 SGLang rollout”、128×128 block-FP8 权重（约 126.7 GB）和 `fp8_e4m3` KV 后，每卡 rollout 权重约 17.1 GiB，并建立了 1,815,954-token KV pool。
- FP8 ToolRL 已完成一次 6,008-token 单组的 rollout、4 次 actor forward/backward 和 TE FusedAdam optimizer step。32M-element optimizer groups 使第一步 state 初始化从 64M 配置的 24 MiB OOM 边界内退回；短探针 HBM 峰值为 141,869/143,771 MiB。它推翻“122B/8卡一定不能做 ToolRL”，但只证明短上下文容量，不代表 16K 上界或 94K 全数据已通过。GAD 还需在线 discriminator，继续单独 fail-closed。

## 最终 122B profile

| 维度 | 配置 | 原因 |
|---|---|---|
| model parallel | TP2 / PP4 / CP1 | TP2 满足 2 个 KV query groups；PP4 切参数与 optimizer；CP1 避免 optimizer 复制 |
| expert parallel | EP2 / ETP1 | `ETP×EP×PP=8`，完整使用 8 rank |
| dispatcher | ordinary all-to-all | 单机 NVLink、DP1；避免 DeepEP 附加 buffer |
| activation | full recompute, uniform, 1 layer | 以计算换 HBM |
| dynamic batching | 8192 tokens/GPU，短 gate 为 4608 | 这是打包目标，不会自动切断一条 94K 样本 |
| parameter gather | FP8 E4M3, delayed recipe | 显著降低参数驻留；blockwise 在 pinned MCore 上不可用 |
| optimizer | precision-aware TE FusedAdam | CPUAdam 的 FP32 state 需要超过本机 1 TiB host |
| optimizer dtype | grad BF16 / main FP16 / m1 FP8 / m2 FP8 | 当前可运行的最低容量组合 |
| state lifecycle | pageable CPU moment offload；train-only SFT gate 为 64M-element groups，colocated RL 为 32M；逐组 eviction；FP16 master weights 保留在 HBM | 同时避开首步 HBM 瞬态和 1 TiB host 峰值 |
| allocator | `expandable_segments:True`（train-only） | 降低首步 2–3 GiB allocator fragmentation；不能用于 TorchMemorySaver colocated rollout |

SFT 的 moments-only CPU 驻留实测使全节点 host used 为 489.14 GiB。若再 offload FP16 master weights，默认 Ray 95% gate 在 975.59/1025.39 GiB 杀 actor，Ray 99% gate仍在 1016.10/1025.39 GiB 杀 actor；所以该组合不是安全配置。checkpoint 保存仍是独立 gate：本报告没有用一次不保存的 step 推断约 244 GB checkpoint 序列化一定安全。

## FP8 rollout 修正路径

- 官方 `Qwen/Qwen3.5-122B-A10B-FP8` 下载已启动；公网/Xet 实测约 5–6 MB/s，完整约 125 GB，不能作为当日容量 gate 的关键路径。
- Slime 自带 `tools/convert_hf_to_fp8.py` 原实现会跳过 Qwen3.5 的 fused expert 键 `experts.gate_up_proj/down_proj`，错误输出几乎仍是 BF16。转换器已修复为逐 expert 拆分 gate/up/down、生成 `weight_scale_inv`，并正确写 index tensor bytes。
- Qwen 官方 FP8 使用 128×128 block、dynamic activation，并在量化前把 scale 舍入 BF16。修正版增加 `--scale-dtype bfloat16`；抽取 layer 4 / expert 0 与官方下载 shard 对照，FP8 weight 和 BF16 scale 均 bit-exact。
- 最终转换命令：

```bash
CUDA_VISIBLE_DEVICES=0 python tools/convert_hf_to_fp8.py \
  --model-dir /root/slime_sxy/group-space/huggingface/zskj-hub/models--Qwen--Qwen3.5-122B-A10B \
  --save-dir /root/slime_sxy/group-space/sunxiangyu/slime_wd/data/Qwen3.5-122B-A10B-FP8-local \
  --strategy block --block-size 128 128 --scale-dtype bfloat16 --max-workers 2
```

容量含义：BF16 rollout 的完整 checkpoint 为约 250.17 GB，即 TP8 仅裸权重就约 31.3 GB/GPU；旧探针把 static fraction 压到 0.10（约 14 GB/GPU 总预算），权重能完成 loader 路径但不可能再建立 KV pool。FP8 tensor data 为约 126.7 GB，TP8 初始实测驻留约 17.1 GB/GPU；static 0.25 约给 35 GB/GPU，总体上重新留下约 18 GB/GPU 给 runtime、Mamba state 与 FP8 KV。这就是 FP8 能改变结论的资源来源，不是继续压低 context 的小修小补。

## FP8 ToolRL 容量 gate

单组探针固定 `RBS=1,n=4,GBS=4`、`prompt/context/response=16384/16448/64`，实际抽中 prompt 5,944 tokens、每条 response 64 tokens，总训练 tokens 6,008。演进如下：

1. FP8 rollout 首次建立 1,815,954-token KV pool；SGLang TP8 custom all-reduce 在 CUDA graph 输入共享时触发 `CUDA invalid argument`。
2. `--sglang-disable-custom-all-reduce` 保留 CUDA graph、改走 NCCL；rollout、4 次 forward/backward 均完成，但 TE Adam 首次 lazy state 初始化被 TorchMemorySaver 的 1 GiB margin 拒绝一笔 24 MiB 临时分配。
3. 把 margin 降到 512 MiB 后仍在同一 24 MiB 边界失败；另一个 3,203-token 对照同样失败，说明主因不是 sequence activation。
4. 把 optimizer parameter group 从 64M 缩到 32M elements（每 rank 约 495–497 groups）后，rollout、4 次 forward/backward 和 optimizer step 全部通过。actor train `164.1 s`，训练吞吐约 `153.1 token/s`；本次四条输出完全相同且 raw reward 都为 -3，GRPO 按定义得到 zero advantage/loss/grad，因此这是容量 gate，不是学习效果证据。
5. v6 在 optimizer metrics 之后的 actor `sleep()` 被 Ray 95% memory monitor 杀死，报告 974.22/1025.39 GiB。Slime 在 pause **之前** 打印的 used/available 为约 528.57/496.82 GiB；两者不是同一时刻，不能据此前值把 Ray 判成误报。
6. v7 把 Ray gate 提到 99% 后，完整 optimizer 仍成功（actor train `155.5 s`，`153.4 token/s`），但第二次 `sleep()` 逐 rank 备份约 120 GiB CUDA allocation 时，raylet 在 12:12:23 记录 cgroup used `1,090,659,237,888` bytes，超过 99% 阈值 `1,089,994,752,000`，随后杀死 rank 2 actor。说明真正瓶颈是训练后 actor pause 的 host 峰值，不是 rollout KV，也不是 Ray 95% 的单纯 RSS 误判。profile 已恢复 95% 保护；不再通过提高/关闭阈值硬挤。

v6/v7 每卡观测峰值达到 141,869 MiB，最紧卡仅余 1,902 MiB。结论边界因此是：**短上下文 ToolRL 的计算通过，但单机 1 TiB host 的 train→rollout 生命周期失败，正式 profile 仍 fail-closed**。需要显式 `ALLOW_UNSUPPORTED_COLOCATED_RL=1` 才能复现计算 gate；即使先做 ≤8K、8–16K、>16K 长度桶，colocated 长跑仍会在每步 pause 重现 host 峰值。正式 ToolRL/GAD 应使用 external rollout engines；仅靠长度截断、FP8 KV 或更低 Ray guard 无法修复这个生命周期瓶颈。

## 正式超参数建议

这些是“通过方法级单组 gate 后的首轮值”，不是建议直接无人值守跑满。

| 方法 | 27B / 4卡 | 35B / 4卡 | 122B / 8卡 |
|---|---:|---:|---:|
| SFT LR | 1e-6 → 1e-7 cosine | 2e-6 → 2e-7 cosine | 5e-7 → 5e-8 cosine |
| ToolRL LR | 1e-7 constant | 2e-7 constant | 5e-8 constant |
| GAD generator LR | 5e-8 constant | 1e-7 constant | 2e-8 constant |
| Adam | β1=0.9, β2=0.95, wd=0.1, grad clip=1 | 同左 | 同左 |

### SFT（364 trajectories，约 8.7M tokens）

- 首轮 1 epoch，而不是因“只有 364 条”盲目多 epoch；`RBS=364, GBS=4`，共 91 updates。
- warmup 3%，cosine decay；Qwen3.5 loss mask，只优化 assistant target tokens；按有效 target tokens 报 loss 和吞吐。
- shortest 已通过；仍须分别通过 p50、p95/最大长序列和 checkpoint-save。不能由 4501 tokens 外推到 94K。
- held-out 按 task type、tool name 和 decision type 分层；migration audit 用于审计，rejected records 不进入训练。

### ToolRL（3182 decisions；短上下文只通过计算 gate，正式训练必须外置 rollout）

- Slime 恒等式：每 rollout 产生 `RBS×n` samples，并应能被 `GBS` 整除。27B/35B 用 `RBS=2,n=4,GBS=8`；122B 无论短上下文 colocated 臂还是 actor/rollout 分离臂，都从 `RBS=1,n=4,GBS=4` 起。
- GRPO，temperature 1.0，entropy 0，clip low/high 0.20/0.28；当前 official ToolRL arm 不加 reference KL。
- `rollout_max_prompt_len=98304`、response=4096、context=102400；探针可把 response 降到 128/256，但正式值不能沿用旧的 6144/2048 截断。
- 先跑 1 个 dataset pass；若全同 reward group >20%，先修 reward/提高采样多样性，不提高 LR。cold start 为主臂，SFT warm start 为对照臂；warm start 用 `--finetune --no-load-optim --no-load-rng`。

### GAD（3147 decisions；必须外置 rollout 与 discriminator）

- Stage 2：从真实 SFT generator 生成 aligned negatives；0.8B discriminator 完整 warmup 1 epoch并保存 manifest；Stage 3 再从同一 SFT checkpoint 分叉，不能接 ToolRL checkpoint。
- generator 从 `RBS=1,n=4,GBS=4`（122B）开始；temperature 0.8；low-var KL coefficient 0.001；reward 权重 discriminator/format/tool=`0.8/0.1/0.1`，最终 clip=2.0。
- discriminator context 先 8192，并记录截断率；单条 negative 或单 pair accuracy 只验证接口，不证明 GAD 有效。
- 0.8B discriminator 不能常驻第 8 张 GPU：ToolRL gate 的最紧 rank 已只余约 1.9 GiB。CPU service 也不是当前 1 TiB 节点的安全退路，因为仅 actor 的 train→rollout backup 就已经超过 99% host 阈值。launcher 保留的 `GAD_DISCRIMINATOR_DEVICE=cpu` 只供较小模型/独立资源探针使用；122B 生产方案应把 rollout engines 与 discriminator 放到额外 GPU 节点，并把权重同步和故障恢复作为独立 gate。

## 数值与资源验收

长跑前必须同时满足：

- loss、grad norm、权重更新均有限且无 NaN/Inf；至少与 27B/35B BF16 路径对照短程趋势。
- SFT 通过长序列与 checkpoint-save；RL 通过 rollout→reward→nonzero advantage→actor optimizer→权重同步→SGLang restore 的完整闭环。
- HBM 最紧 rank 至少留 5–10 GiB，host steady state至少留 128 GiB；不得通过关闭 Ray OOM 保护掩盖容量不足。
- FP8 optimizer path 是本项目补丁，升级 Transformer Engine/Megatron-Core 后必须重跑 blockwise/delayed compatibility 和单步等价性测试。
