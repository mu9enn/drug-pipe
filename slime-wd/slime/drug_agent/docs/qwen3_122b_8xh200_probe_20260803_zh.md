# Qwen3.5-122B-A10B：8×H200 转换与训练探针报告

日期：2026-08-03。worker：`slime-train-8g128c-40967252-cfcd2`，8×NVIDIA H200（每卡 143771 MiB），host RAM 1025 GiB。

## 结论

- HF→Slime torch distributed checkpoint 已成功：16 个 `.distcp` 文件，共 244,319,908,688 bytes；tracker 为 `release`。训练时已从转换用 `TP1/PP8` 成功重分片加载到 `TP2/PP4/EP2`。
- `TP2/PP4/CP1/EP2/ETP1` 能在 8×H200 上完成 4501-token canonical SFT 的真实 forward/backward；一次 microbatch 为 27–33 秒。
- Slime 官方推荐的大 MoE 低精度主路径是 BF16 训练 + FP8 rollout，但单机 8×H200 无法容纳本模型的标准 BF16 全参 Adam。本文采用的是实验性容量路径：FP8 parameter gather、FP16 main params、BF16 main grads、FP8 Adam moments、完整 optimizer-state CPU offload。它必须以数值稳定性对照验证，不能等同于官方生产精度路径。
- pinned Megatron-Core/Transformer Engine 的 `blockwise` FP8 与 FP16 optimizer shard 不兼容；本环境必须用 `--fp8-recipe delayed`。
- 标准 TE FusedAdam 会让第一步已初始化的全部 moments 累积驻留 GPU，实测最后在 139.98/140.06 GiB 硬 OOM。项目补丁改为每个 bounded parameter group 更新后立即把 FP8 moments 的 raw bytes 转存 CPU，再进入下一组；最终单步结果见下文“最终 gate”。
- ToolRL/GAD 的参数已按 Slime batch 恒等式和本数据长度固化；只有在 SFT optimizer-step gate 通过后，122B colocated rollout 才值得启动。GAD 还需要真实 SFT checkpoint、全量 aligned negatives 和 discriminator warmup，不能用 base checkpoint 冒充完成的三阶段训练。

## 最终 122B profile

| 维度 | 配置 | 原因 |
|---|---|---|
| model parallel | TP2 / PP4 / CP1 | TP2 满足 2 个 KV query groups；PP4 切参数与 optimizer；CP1 避免 optimizer 复制 |
| expert parallel | EP2 / ETP1 | `ETP×EP×PP=8`，完整使用 8 rank |
| dispatcher | ordinary all-to-all | 单机 NVLink、DP1；避免 DeepEP 附加 buffer |
| activation | full recompute, uniform, 1 layer | 以计算换 HBM |
| dynamic batching | 8192 tokens/GPU，短 gate 为 4608 | 这是打包目标，不会自动切断一条 94K 样本 |
| parameter gather | FP8 E4M3, delayed recipe | 显著降低参数驻留；blockwise 在 pinned MCore 上不可用 |
| optimizer | precision-aware TE FusedAdam | CPUAdam 的 FP32 state 需要超过本机 1 TiB host |
| optimizer dtype | grad BF16 / main FP16 / m1 FP8 / m2 FP8 | 当前可运行的最低容量组合 |
| state lifecycle | 完整 CPU offload；64M-element groups；逐组 moment eviction | 避免首步瞬态和 colocated steady-state HBM OOM |
| allocator | `expandable_segments:True`（train-only） | 降低首步 2–3 GiB allocator fragmentation；不能用于 TorchMemorySaver colocated rollout |

预计完整 optimizer CPU 驻留上限约 455 GiB；host preflight 设 900 GiB，GAD 设 1000 GiB，另留 128 GiB reserve。checkpoint 保存仍是独立 gate：本报告没有用一次不保存的 step 推断 244 GB checkpoint 序列化一定安全。

## 正式超参数建议

这些是“通过方法级单组 gate 后的首轮值”，不是建议直接无人值守跑满。

| 方法 | 27B / 4卡 | 35B / 4卡 | 122B / 8卡 |
|---|---:|---:|---:|
| SFT LR | 1e-6 → 1e-7 cosine | 2e-6 → 2e-7 cosine | 5e-7 → 5e-8 cosine |
| ToolRL LR | 1e-7 constant | 2e-7 constant | 5e-8 constant |
| GAD generator LR | 5e-8 constant | 1e-7 constant | 2e-8 constant |
| Adam | β1=0.9, β2=0.95, wd=0.1, grad clip=1 | 同左 | 同左 |

### SFT（364 trajectories，约 8.7M tokens）

- 首轮 1 epoch，而不是因“只有 364 条”盲目多 epoch；`RBS=364, GBS=4`，共 91 updates。
- warmup 3%，cosine decay；Qwen3.5 loss mask，只优化 assistant target tokens；按有效 target tokens 报 loss 和吞吐。
- 先分别通过 shortest、p50、p95/最大长序列和 checkpoint-save 四个 gate。122B shortest 成功不能外推 94K。
- held-out 按 task type、tool name 和 decision type 分层；migration audit 用于审计，rejected records 不进入训练。

### ToolRL（3182 decisions）

- Slime 恒等式：每 rollout 产生 `RBS×n` samples，并应能被 `GBS` 整除。27B/35B 用 `RBS=2,n=4,GBS=8`；122B 从 `RBS=1,n=4,GBS=4` 起。
- GRPO，temperature 1.0，entropy 0，clip low/high 0.20/0.28；当前 official ToolRL arm 不加 reference KL。
- `rollout_max_prompt_len=98304`、response=4096、context=102400；探针可把 response 降到 128/256，但正式值不能沿用旧的 6144/2048 截断。
- 先跑 1 个 dataset pass；若全同 reward group >20%，先修 reward/提高采样多样性，不提高 LR。cold start 为主臂，SFT warm start 为对照臂；warm start 用 `--finetune --no-load-optim --no-load-rng`。

### GAD（3147 decisions）

- Stage 2：从真实 SFT generator 生成 aligned negatives；0.8B discriminator 完整 warmup 1 epoch并保存 manifest；Stage 3 再从同一 SFT checkpoint 分叉，不能接 ToolRL checkpoint。
- generator 从 `RBS=1,n=4,GBS=4`（122B）开始；temperature 0.8；low-var KL coefficient 0.001；reward 权重 discriminator/format/tool=`0.8/0.1/0.1`，最终 clip=2.0。
- discriminator context 先 8192，并记录截断率；单条 negative 或单 pair accuracy 只验证接口，不证明 GAD 有效。
- 在线 GAD 比 ToolRL 多一个 discriminator service，且本 worker 的 1025 GiB host 只比 1000 GiB gate 高约 25 GiB；即使 SFT 成功，也应把 GAD 视为最紧的实验配置。

## 数值与资源验收

长跑前必须同时满足：

- loss、grad norm、权重更新均有限且无 NaN/Inf；至少与 27B/35B BF16 路径对照短程趋势。
- SFT 通过长序列与 checkpoint-save；RL 通过 rollout→reward→nonzero advantage→actor optimizer→权重同步→SGLang restore 的完整闭环。
- HBM 最紧 rank 至少留 5–10 GiB，host steady state至少留 128 GiB；不得通过关闭 Ray OOM 保护掩盖容量不足。
- FP8 optimizer path 是本项目补丁，升级 Transformer Engine/Megatron-Core 后必须重跑 blockwise/delayed compatibility 和单步等价性测试。
